## 4. Token & Cost Correlation

**Counterintuitively, no — not in raw dollar terms.** Claude + Edgee cost **$2.01 more (+19.6%)** despite better plan efficiency. Understanding why requires unpacking the token breakdown:

Key observations:

1. **Claude + Edgee ran 5.5 more effective instructions** — it *should* cost more in absolute terms because it did more total work. The cost-per-instruction story is more favorable than the headline number.
2. **Output tokens are 48% higher** in Claude + Edgee despite input tokens being nearly equal. This suggests the model was less constrained in generating responses when context pressure was lower — it produced richer, more complete outputs per instruction.
3. **Cache reads are 17% higher** in Claude + Edgee, consistent with a longer session reaching more instructions and accumulating more reusable cached context over time.
4. **Plan consumption is not purely a token-count metric** — it reflects Anthropic's internal rate-limiting heuristics, which appear to weight conversation context length and complexity, not just raw API token volume. This is why Claude + Edgee can show *more* output tokens yet *less* plan consumption: the compression reduces the *context* sent in each turn, which is the apparent lever.

## 5. Why Claude + Edgee Helps

Based on the data, the most likely mechanism is **context compression reducing per-turn context size, not simply reducing token count.**

### Evidence:


| Signal                                                              | Interpretation                                                                                                                    |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Input tokens nearly identical (+5.3%) despite 5.5 more instructions | Compression actively shrinks growing conversation context; without it, input tokens would grow much faster as history accumulates |
| Output tokens significantly higher (+48%)                           | Model has more "headroom" per turn when context isn't bloated — produces fuller responses                                         |
| Per-instruction plan % lower despite more outputs                   | Plan rate-limit is driven more by context window pressure than output length                                                      |
| Spike dampening (max Δ 7 vs 9)                                      | Removing redundant/verbose context prevents occasional large-context turns from spiking usage                                     |


### Hypothesis:

Without Edgee, Claude Code sends the **full accumulated conversation history** with each request. As the session progresses, this context grows substantially, and each instruction consumes an increasing share of the plan budget — explaining why baseline Claude's late-session instructions (17–21) all show Δ5–7pp.

Edgee's compression gateway **truncates or summarizes older conversation turns** before they reach the model, keeping per-turn context size roughly stable across the session. This means:

- The plan sees a roughly **constant cost per instruction** rather than an accelerating one
- Input tokens stay flat (compressed history ≈ same size at instruction 26 as at instruction 6)
- The model's output quality isn't degraded (output tokens actually *increase*), suggesting the compressed context preserves semantic relevance

This is not primarily a cache efficiency story — cache read ratios are proportionally similar between scenarios. **The gain is architectural: context size control, not cache optimization.**
